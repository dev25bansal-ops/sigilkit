## 1. 一分钟上手

```bash
npm run setup        # 首次：检查 Node/npm/Foundry，装依赖，构建所有 workspace
npm run verify       # 提交前的全量守门（步骤见 §3）
npm run verify:quick # 快版：跳过 forge
```

`verify` 是唯一的"我改完了，能提交了吗"入口。其余脚本都是被它调用的分步实现，或面向专项排查的工具。

> **本机环境提示。** 这台机器的 reparse point 机制是坏的 —— 三种建链方式
> （`symlinkSync('junction')` / `symlinkSync('dir')` / `cmd mklink /J`）都能建成**结构完好但无法遍历**的
> 链接，`readdir`/`readFile` 一律抛 `UNKNOWN errno=-4094`。因此 `npm install` 建的
> `node_modules/@sigilkit/*` 工作区链接在本机不可用，依赖树处于残缺状态。
> **先跑 `node scripts/check-reparse-points.mjs` 确认宿主能力**，再决定是否走"删链接重装"这条路。
> 详见 `docs/TROUBLESHOOTING.md` → "A path check says a file is fine, but reading or listing it fails"。

## 3. `verify.mjs` 的 10 个步骤

`npm run verify -- --list` 的实际输出（键 = 可粘贴的 `--only=` 选择器）：

| 键 | 标签 | 超时 | 为什么存在 |
|----|------|------|-----------|
| `lint` | workflow lint | 60s | actionlint over `.github/workflows` |
| `packaging` | container packaging | 60s | 静态 Dockerfile 不变量（不 build 镜像） |
| `helpers` | helper suites | 300s | 守门脚本自身的回归测试 |
| `docs` | doc counts | 60s | 文档里的数字仍与代码一致 |
| `docslocation` | doc location | 600s | 没有 `.md` 流浪在 `docs/` 之外（那样它不会被索引、也不会进包） |
| `build` | workspace build | 600s | `dist/*.d.ts` 已生成 |
| `typecheck` | workspace typecheck | 600s | 各 workspace 的 `tsc` |
| `artifacts` | package artifacts | 120s | 入口与 `dist` 布局可解析 |
| `contracts` | contract tests (unit + fuzz) | 3600s | `forge test`，排除 invariant 与 fork |
| `tests` | TypeScript tests | 1800s | 各 workspace 测试套件 |

常用调用：

```bash
npm run verify -- --list                      # 列出步骤
npm run verify -- --only=docs                 # 只跑一步
npm run verify -- --quick                     # 跳过 forge（--quick 隐含 --no-forge）
npm run verify -- --json                      # stdout 纯 JSON，人类表格走 stderr
npm run verify -- --only=nonexistent          # → 退出码 2，提示跑 --list
VERIFY_STEP_TIMEOUT="lint=60000" npm run verify   # 覆盖某步超时
```

`verify` 自身会打印一段固定提醒：`not covered by npm run verify (CI-only): slither, gitleaks, halmos, fork, deep-fuzz` —— 本地全绿 ≠ CI 全绿。

## 4. 耗时盘点（本机实测，2026-09-26）

| 脚本 | 实测 | 判断 |
|------|------|------|
| `check-runtime` | 0.05s | 快 |
| `check-vectors` | 0.05s | 快 |
| `check-dockerfile` | 0.05s | 快 |
| `check-package-artifacts` | 0.05s | 快 |
| `clean --dry` | 0.06s | 快 |
| `sync-facts` | 0.08s | 快 |
| `check-waivers` | 0.11s | 快 |
| `validate-workflows` | 0.12s | 快 |
| `assurance-inventory --compact` | 0.39s | 快 |
| `benchmark-indexer --rows=50 --reps=1` | 1.22s | 默认参数（1000×3）会更久 |
| `verify --only=artifacts` | 0.23s | 快 |
| `verify --only=packaging` | 0.26s | 快 |
| `verify --only=lint` | 0.30s | 快 |
| `forge test --list` | ~15.8s（含 14.5s 编译） | 冷编译一次；之后走 forge 缓存 |
| `verify --only=docs` | 23.6s | **>10s**。内部至少 2 次 `execFileSync(FORGE, …)`（`test --list` + 2 次 `config --json`），冷编译时被放大 |
| `verify --quick --json` | 106s | **>10s**。9 步里最慢的是 `build`/`typecheck`/`tests`（各 600/1800s 预算） |

**超过 10 秒的两个入口，以及能否优化：**

- **`check-doc-counts`（23.6s）** — 可优化。它对同一份 forge 配置重复 `execFileSync`：`forge test --list` 一次、`forge config --json` **两次**（`resolvedFoundryConfig("ci")` 与 `("default")`）。三次调用之间编译产物本可复用。建议：先 `forge build` 一次（或直接读 `foundry.toml` + `forge config` 的合并结果），再只做一次 `test --list`。冷编译去掉后可省下大部分 23.6s。
- **`verify --quick`（106s）** — 部分可优化。`--quick` 已经跳过 forge，剩下的时间几乎全在三个 npm workspace 步骤（`build` → `typecheck` → `tests`），它们各自要起一遍 `tsc`/vitest。`build` 与 `typecheck` 有重叠（build 通常已经跑过 tsc），可以考虑让 `typecheck` 复用 `build` 的增量产物，或在 `--quick` 下把 `build` 与 `typecheck` 合并为一步。收益中等，改动成本不低。

其余单脚本都在 0.5s 以内，属于"随手跑"级别。

## 5. `--help` 支持率与输出质量

**支持并正确处理 `--help` 的只有 3 个（占可执行脚本的 3/14 ≈ 21%）：**

| 脚本 | 质量评价 |
|------|----------|
| `assurance-inventory.mjs` | **最好**。有 Usage、逐条 Options（`--root`/`--compact`/`-h`）、并明确声明 `Mode: STATIC_INVENTORY` 与"不执行任何工具"的安全边界 |
| `clean.mjs` | **好**。单行 usage + 4 个 flag 各一行说明，含 `--dry`/`--yes` 的语义 |
| `benchmark-indexer.mjs` | **好**。Usage + `--rows/--reps/--seed` 范围与默认值 + 输出路径 + Node 版本要求 |

**不支持 `--help` 的 11 个**，其中两类行为截然不同：

**(a) 报错退出（可接受）—— `sync-facts.mjs`、`verify.mjs`**

```
$ node scripts/sync-facts.mjs --help
sync-facts: unrecognized argument "--help"
usage: sync-facts [--check] [--write] [--list] [--strict] [--json] [--root=<dir>]
# 退出码 2
```
参数校验严格、报错带 usage，属于正确的 fail-fast。但 `--help` 本身不被接受，是可用性上的小缺陷。

**(b) 静默忽略 `--help` 并执行真实检查（更糟）—— 7 个**

以下脚本完全不读 `process.argv`，传 `--help` 会被**当成正常运行**，跑完真实的校验并打印结果：

| 脚本 | `node scripts/<x>.mjs --help` 的实际结果 |
|------|----------------------------------------|
| `check-doc-counts.mjs` | 跑完整文档计数校验（默认只读，改写需显式 `--write`——已实测无参运行不会触碰文件） |
| `check-vectors.mjs` | 打印向量语料 OK |
| `check-waivers.mjs` | 打印 waiver check OK |
| `validate-workflows.mjs` | 打印 workflow validation OK |
| `check-dockerfile.mjs` | 打印 dockerfile OK |
| `check-package-artifacts.mjs` | 跑完整产物检查 |
| `check-runtime.mjs` | 跑完整运行时诊断 |
| `bootstrap.mjs` | **危险**：会真的执行安装/构建 |
| `generate-vectors.mjs` | **危险**：会真的写 `vectors/*.json` |

这类"忽略未知参数"比"拒绝未知参数"更难排查：开发者敲 `--help` 想看用法，却意外触发了一次真实操作（`generate-vectors` 甚至直接覆写文件）。

**其他可发现性缺口：**

- `verify.mjs` 和 `sync-facts.mjs` 内部**已有**完整 usage 字符串（`verify` 的 `USAGE` 还被测试断言覆盖），只是没接到 `--help` 上。
- 7 个脚本的**用法与参数只存在于源码顶部的 JSDoc 注释**里（如 `bootstrap.mjs` 头部列了 `--no-install` / `--no-build` / `--install`），CLI 上完全看不到。
- `_dbg.mjs` 是一个遗留的一次性调试脚本（880 字节，在 `%TEMP%` 建临时目录），不属于工具链，建议删除或移入 `scripts/_debug/`。

## 6. 跨平台：两个 `.sh` 安装脚本

仓库里有两个 shell 脚本，**都只服务 CI，从未被 `package.json` 引用**：

| 脚本 | 被谁调用 |
|------|----------|
| `scripts/install-actionlint.sh` | `.github/workflows/ci.yml:83` — `echo "bin=$(bash scripts/install-actionlint.sh)" >> "$GITHUB_OUTPUT"` |
| `scripts/install-gitleaks.sh` | `.github/workflows/ci.yml:141`、`publish.yml:73` |

**结论：Windows 上不会因为 `npm run` 而失败。** 两者都不在任何 `npm` script 里，只在 `runs-on: ubuntu-latest` 的 job 里以 `bash` 调用。它们锁定 `linux_x64` / `linux_amd64` 的下载 URL，即使在 Windows 上装了 bash 也会下错平台的包。

**Windows 本地开发的影响是"能力缺失"而非"构建失败"：**

- 本地跑 `npm run verify` 时，`lint` 步骤依赖 `actionlint` 二进制。Windows 上没有等价的 `actionlint`（官方只发 linux/macOS/Windows 各自平台的包），所以本地 `lint` 步骤要么跳过、要么失败——**这也是 `verify --list` 里明确列出 `slither, gitleaks, halmos, fork, deep-fuzz` 为 CI-only 的同一类问题**。
- 两个脚本的安全设计（先校验 SHA256 再 `tar` 解包、把二进制写进 runner scratch dir 而非工作树、stdout 只输出路径）都是对的，值得保留。

**可选的跨平台方案（按成本排序，本次未实施）：**

1. **Node 等价物（推荐）** —— 把两个安装脚本改写为 `scripts/install-actionlint.mjs` / `scripts/install-gitleaks.mjs`，用内置 `fetch` 下载、`node:crypto` 算 SHA256、按 `os.platform()` 选资产名、解包用 `node:zlib` + `tar`（或调 `tar.exe`）。CI 侧把 `bash scripts/xxx.sh` 换成 `node scripts/xxx.mjs`。好处是 Windows/macOS/Linux 同一份代码，保留全部安全属性，且顺带能用上 `check-runtime` 的平台诊断。
2. **PowerShell 等价物** —— 为 Windows 开发者提供 `install-*.ps1`，仅本地自用，CI 继续用 `.sh`。成本最低（两个脚本各约 20 行），但不减少维护面。
3. **包管理器分发** —— 改用 npm 依赖（如 `@rhysd/actionlint` 包装包）让 `npm run` 自动带上，彻底不需要安装脚本。代价是引入第三方供应链面，与当前"锁定 + 校验和"的安全立场冲突。
4. **维持现状** —— 在 `docs/TROUBLESHOOTING.md` 里写明"本地 `lint` 需要 actionlint，Windows 用户请用 WSL"。零成本，但 DX 打折。

**本机环境事实（供参考）**：`bash` 存在但是 `C:\WINDOWS\system32\bash.exe`（WSL 启动器），并非 Git Bash；`pwsh` 可用；仓库内除 `outputs/_gloss_survey.ps1` 外无任何 `.ps1` 文件。

## 7. `package.json` scripts 评估

现有 19 个 script（含 `test` 这个 npm 生命周期 script）。

**命名一致性 —— 三套前缀混用：**

| 前缀 | 成员 |
|------|------|
| `check:*` | `check:artifacts`、`check:docs`、`check:docs:full` |
| `lint:*` | `lint:workflows`、`lint:docker` |
| 动词裸名 | `setup`、`verify`、`build`、`test`、`clean`、`demo`、`fleet`、`mcp` |
| 领域裸名 | `test:full`、`test:coverage`、`test:helpers`、`vectors:generate` |

`check:docs` 与 `lint:docs` 语义重叠但只存在前者；`lint:workflows` 做的其实是"结构校验"（`validate-workflows.mjs`），而 `verify` 里同一个步骤的标签叫 `workflow lint`（那里才是真 `actionlint`）——**同名不同物**，容易误解。

**重复 / 冗余：**

- `verify.mjs` 的 9 个步骤已经覆盖了 `lint:workflows`、`lint:docker`、`check:artifacts`、`check:docs`、`test:helpers` 的全部职责，这些顶层 script 属于"绕过 `verify` 直接跑一步"的快捷方式——可接受，但 `test:helpers` 传的 `--only=helper`（单数）与真实步骤键 `helpers`（复数）不一致，只因 `matchesOnly` 恰好做子串匹配才没报错；一旦选择器改成精确匹配就会断。
- `test` 与 `test:full` 仅差 `--no-match-contract ".*Fork"` 一处，且都硬编码 `forge`，Windows 上无 `forge` 时直接失败。
- `check:docs:full` 只是 `check:docs --with-ts` 的别名，重复定义可以接受但命名上未体现"更慢"。

**隐藏的关键命令（存在但未暴露到 `package.json`）—— 6 个：**

| 脚本 | 为什么该暴露 |
|------|--------------|
| `check-vectors.mjs` | 改了向量就必须跑，但没有任何 `npm run` 入口 |
| `check-waivers.mjs` | 加 `continue-on-error` 的守门人，只有 `verify` 间接覆盖 |
| `check-runtime.mjs` | 环境问题排查入口，README 级 troubleshooting 工具 |
| `sync-facts.mjs` | 改 `engines.node` 后的标准动作，当前只能手敲 `node scripts/…` |
| `assurance-inventory.mjs` | 审计证据生成，评审/合规场景需要 |
| `benchmark-indexer.mjs` | 性能基线，性能评审场景需要 |

**缺失的常用入口：**

- `format` —— 全仓库无格式化配置与脚本。
- `test:watch` —— 无 watch 模式。
- `docs` —— 没有"生成/校验文档"聚合入口（`check:docs` 只校验计数）。
- `typecheck` —— 存在但只作为 `verify` 的内部步骤，没有顶层 `npm run typecheck`（而 `build`、`test` 都有）。
- `clean` 有，`clean:all` 之类变体不需要。

**`npm run` 报错友好度 —— 良好：**

```
$ npm run nonexistent
npm error Missing script: "nonexistent"
npm error
npm error To see a list of scripts, run:
npm error   npm run
```

`npm run`（无参）会完整列出全部 19 个 script 及其命令，可发现性没问题。缺的是**分类与说明**——19 行平铺，没有"我该跑哪个"的引导，新人仍需逐行读。

## 8. 输出质量抽样结论

抽样脚本：`verify.mjs`、`sync-facts.mjs`、`check-doc-counts.mjs`、`check-package-artifacts.mjs`、`check-waivers.mjs`、`clean.mjs`、`assurance-inventory.mjs`、`benchmark-indexer.mjs`。

**失败时可诊断性 —— 整体水平明显高于同类项目：**

- `verify.mjs` 最好。失败时给出：失败步骤名、**可直接粘贴的单步复跑命令**（`npm run verify -- --only=helpers`）、超时预算、实际耗时、完整日志文件路径（`outputs/verify/<时间戳>-<步骤>.log`）、以及日志尾部 30 行摘录。
- `sync-facts.mjs` 每条 error 带 `fact` / `actual` / `expected` / `writable`（能否 `--write` 修复）/ `why`（根因解释）/ 修复方式。实测输出示例：

  ```
  ERROR scripts/bootstrap.mjs:34  [node-floor.fragile-parse]
        fact:     node engine floor
        actual:   24 today, 10 for a three-digit major
        expected: 24
        writable: no — asserted only, fix by hand
        why:      digit-slice floor: every digit is concatenated, then the first two are
                  kept, so ">=100" becomes 10. …
  ```
  这是本次审计中质量最高的失败输出——不只说"failed"，而是给出根因、影响和"能不能自动修"。
- `check-doc-counts.mjs` 失败时逐条列出 `README says X, actual is Y`，并提示 `--write` 的边界（哪些能自动改、哪些必须手改）。
- `check-waivers.mjs` 直接指向 `docs/CI-WAIVERS.md` 的规则编号。
- `check-vectors.mjs` 提示 `npm run vectors:generate`。

**共性问题：**

- `check-doc-counts.mjs` 跑不了 `forge test --list` 时**直接 `process.exit(2)`**，只打印一行"could not run forge…Set FORGE_BIN"，不告诉用户哪些检查因此被跳过——"跳过了什么"比"失败了"更重要。
- `bootstrap.mjs` 虽有清晰的分步输出（`1/4 Node.js` 等），但**默认是破坏性的**（真装依赖、真构建），且 `--help` 被静默忽略（见 §5）。没有 `--dry`。

**机器可读输出（`--json`）—— 4 个脚本支持：**

| 脚本 | `--json` 行为 | 非 TTY 下有无 ANSI 转义 |
|------|--------------|:----------------------:|
| `verify.mjs` | stdout 纯 JSON，人类表格转 stderr | 否 |
| `sync-facts.mjs` | stdout 纯 JSON | 否 |
| `check-package-artifacts.mjs` | stdout 纯 JSON（`{root, results, errors, warnings}`），异常路径也输出合法 JSON | 否 |
| `check-runtime.mjs` | stdout 纯 JSON（报告 + verdict） | 否 |
| `assurance-inventory.mjs` | **默认即 JSON**，`--compact` 出单行 | 否 |

实测 3 个 `--json` 脚本输出均能被 `ConvertFrom-Json` 成功解析，且重定向到文件后**不含 ESC 字节**。

**注意：其余 9 个可执行脚本全部没有 `--json`**，只能解析人类可读文本。若要 CI 聚合（把 9 个 `check-*` 的结果汇成一份报告），需要给它们补 `--json`——否则只能靠正则刮文本。

**进度输出在非 TTY 下的降级 —— 良好：**

- `verify.mjs` 有一套显式的颜色决策（`NO_COLOR` > `FORCE_COLOR` > `TERM=dumb` > `CI` > 非 TTY），注释明确说明"CI 即使是伪终端也必须关色"。实测 4 个脚本重定向到文件后 `hasESC=False`。
- `verify.mjs` 的表格用了 `│` 制表符前缀，**失败时把完整子进程输出落到日志文件**、终端只留 30 行摘录——这是正确的降级思路：CI 日志不会被几十万行测试输出淹没。
- 少数脚本的日志行仍带 `│` 前缀，属于装饰性噪声但在非 TTY 下无害。

**正常路径噪声 —— 基本无问题：**

- 所有脚本的成功路径都是 1-6 行摘要（实测 `check-waivers`/`validate-workflows` 各 1 行，`check-vectors` 6 行），没有进度条、没有逐文件刷屏。
- 唯一的噪声源是 `verify` 跑 helper 套件时把 `node --test` 的 TAP 输出全量透传（本机约 30 秒、数百行）。它已落盘到日志并在终端截断，属于可接受的设计。

## 9. 汇总：发现与建议（本次只报告，未改动）

**高优先级**

1. **7 个脚本静默忽略未知参数**，其中 `generate-vectors.mjs` / `bootstrap.mjs` 会被 `--help` 触发真实写操作。建议全部改为"未知参数即报错 + 打印 usage"，`--help` 单独处理。
2. **6 个关键脚本未暴露到 `package.json`**（`check-vectors`、`check-waivers`、`check-runtime`、`sync-facts`、`assurance-inventory`、`benchmark-indexer`），新工程师只能靠翻源码发现。
3. **`test:helpers` 的 `--only=helper` 与真实步骤键 `helpers` 不一致**，目前靠子串匹配侥幸生效。

**中优先级**

4. `check-doc-counts.mjs` 重复调用 `forge` 三次，23.6s 可优化到个位数秒。
5. **9 个脚本缺 `--json`**，CI 无法聚合结果。
6. `check-doc-counts.mjs` 在 `forge` 不可用时 `exit(2)` 却不说明"哪些检查被跳过"。
7. `package.json` 三套前缀混用（`check:*` / `lint:*` / 裸动词），且 `lint:workflows` 与 `verify` 的 `workflow lint` 同名不同物。
8. 缺 `typecheck`（有 `build`/`test` 却无 `typecheck` 顶层入口）、`format`、`test:watch`、`docs` 入口。

**低优先级**

9. `verify.mjs` / `sync-facts.mjs` 内部已有 usage 字符串，接上 `--help` 是零成本改动。
10. `_dbg.mjs` 是遗留调试脚本，建议删除。
11. Windows 上无 actionlint/gitleaks 等价路径；两个 `.sh` 仅 CI 用，不影响 `npm run`，但本地 `lint` 能力缺失。
12. `verify --quick` 106s 中 `build` 与 `typecheck` 有重叠，可考虑合并。
