### 2.2 关键发现：111/120 处是误报

**`完全`（55 处）全部是技术断言，不是空洞表述。** 分类抽样：

- `ARCH-CONTRACTS:100` 「不可信区（**完全**外部可控）」→ 信任边界术语，精确。
- `:415` 「它们**永远不会**在同一个地址上执行」→ 结构性事实，可验证。
- `:479` 「**完全遵循**，且是本仓库最扎实的部分」→ 对照 EIP-7702 规范原文的合规声明。
- `VERIFICATION-STRATEGY:51` 「UAT ❌ **完全缺失**」→ 缺口声明，是事实。

**这类用法是正确的技术写作，不应修改。** 把「完全」一律替换为量化描述反而会破坏准确性
（如「完全不触碰 EOA 的 storage」改成「99% 不触碰」是错误的）。

**`改进`（24 处）全部是表格列名**（`| ID | 合约 | P | 改进点 | …`），不是叙述性空洞表述。

   **③ 可派生性会随周边散文改写而失效（dc-stale 提议，本方采纳）**：
   一份「可派生数字」的文档之所以有价值，是因为它能从权威源**重新算出来**；
   但**如果它周边的叙述文字被改写、而派生口径没跟着变，那个数字就悄悄失去可派生性了**
   —— 它看起来仍是派生值，实际已无法从新叙述中重新导出。

   **判据（优先级由 sc-gate 独立得出，比原话更抗衰减）**：
   > **判据优先选机械可判的**（已插值 / 在注释行 / 是常量），语义判据只作交叉验证。
   > 理由：语义会随改写漂移，「有没有插值」不会。

   **审计含义**：复核一份「可派生」文档时，复核对象**不是那个数字本身**，
   而是**「能否从当前散文重新导出这个数字」** —— 即 ③→②→① 依次成立。
   **这正是本轮 P0（D-04）发生的机制**：D-04 的 `isModuleType` 返回值本可由源码派生，
   **但没人重新导出过**，所以它能一直声称「仍是 6」而无人反驳。
   **可派生 ≠ 免于审计——它只改变审计的入口，不改变审计的义务。**

   **操作要点**：`file:line` 行号锚点是第 ③ 环里**最易衰减**的形态（行号会漂）。
   **符号名 + 行号双锚点**（`STYLE-2026-09-26.md:104-107` 定义的规范）是**最低衰减形态**，
   应作为所有新引用的默认。

   **★ 反例：判据的价值不只在于它拦住过什么（dc-stale 补充，非本方原话）**
   上面第 ③ 环描述的是一种**失效模式**。但本轮出现了一个**反向实例**，
   它证明这条判据不是绕口令，而是**划定未被观测的区域**：

   `docs/STALENESS-2026-09-26.md:14` 记着 `docs/*.md` = 51、`vault/*.md` = 22，
   作为 F-16「48/51 未注册」的分母。**dc-stale 重测：仍是 51 与 22**
   （本方已独立复核：`Get-ChildItem` 计数同为 **51 / 22** ✅）。
   ⇒ **散文没改、派生口径没改、派生值也没失效—— 但这条规则真正防的东西，在这次审计里从未发生。**

   > **一条判据的价值不只在于它拦住过什么，也在于它标明了一类
   > 「本来会静默腐烂、而这次恰好没腐烂」的文档。**

   那 40+ 份未注册文档**此刻都还正确** —— **不是因为它们被验证过，而是因为没有人改动过它们。**
   F-16 的措辞「unchecked, not fine」说的正是这件事，而第 ③ 环是它的**机制层**。

   **这条补充把第 ③ 环从「描述一种失效模式」升级为「标明盲区」**——
   后者价值更大：**它告诉你哪里是盲区，而不只是告诉你哪里出过事。**

   > **在环境正在写入时采集的数字，不是基线，是快照。**

   **🔴 门禁退出码不足以区分「内容不对」与「工具没跑」（team-lead 扩展我原话，三种状态）**

   | exit | 含义 | 本轮实例 |
   |---|---|---|
   | **0** | 通过 | 依赖恢复后取得 |
   | **1** | **漂移 _或_ 模块缺失** | 两次 `ERR_MODULE_NOT_FOUND`（`yaml` 包缺 → `yaml/dist/index.js` 缺） |
   | **2** | forge 不可用（fail-loud） | 忘设 `FORGE_BIN` |

   **⇒ 关键：`1` 同时代表「文档数字漂移」与「工具跑不起来」，而两者 stderr 完全不同（计数行 vs 堆栈）。**
   > **退出码是结论，stderr 才是过程。判据必须是「读 stderr」，不是「看 exit code」。**
   **这与第 ⑤条「一个数字不足以区分『值变了』与『采样器坏了』」同构** ——
   **本轮我写得更早，但 team-lead 的推广更完整：它适用于一切「跑一下就有结论」的门禁。**

6. **静态推导必须标注「数据源快照时间」。** 本轮 README 在审计期间被队友更新
   （158/14 → 220/17），导致我的静态数字在写完报告后即失效。
   **对「会变的数据」做的任何断言，都应记录读取时刻，或直接改为实测。**

   **📌 本轮实测到的「快照失效」活实例 —— 且我第一版把它读反了（team-lead 纠正）**：
   我在自查时连续两次跑 `check-doc-counts`，**第一次 exit 1**（`TROUBLESHOOTING: says 56,
   actual is 57`），**第二次 exit 0**，两次相隔不到一分钟。
   **我据此写下「有队友正在并发改合约」并上报为「门禁坏了」—— 这是错的。**
   实情：那是 **ck-arch 的 SEC-10 修复早已完成**（`SessionKeyManager` 的注解数稳定在 8），
   **ck-doc 已把文档同步到 56**；**我上一次的 57 是我自己上一轮的旧测量值**。
   **一次观测只能证明「发生过变动」，不能证明「正在变动」。**
   ⇒ 我的第一反应（"正在并发修改"）**跳过了正确的第一问**（"上一轮那个数是不是我的旧值？"）。
   **收口规范（team-lead 采纳）**：**观测到「某物正在变动」时，先确认它是否仍在变动（再测一次）。**
   ⇒ **本方因此把本报告的所有可验证数字都改为当场实测，并在附录 A 标注复现命令。**

7. **🔴 根因级建议（ck-arch 提出，我方认同并补充设计层面）**：门禁守住**数量**，
   但**没有任何机制守住「内容与代码的一致性」**。这正是 D-04 文档失真的根因 ——
   **不是没人写，而是「没有东西会失败」**。
   本轮实测确认：ERC-7201 槽位断言（`0xff08…` / `0x37ff…` / `0x6092…`）本可被
   `cast index-erc7201` 一行校验，**但至今无门禁**，只能靠人工逐字节比对。
   **建议在 `scripts/check-doc-counts.mjs`（或新建 `check-doc-claims.mjs`）增一组
   「内容断言」门禁**，按成本/收益排序（均已实测可行）：

   | 断言 | 校验方式 | 成本 |
   |---|---|---|
   | ERC-7201 三根槽 | `cast index-erc7201 <id>` vs 源码常量 | 极低（已验证） |
   | `isModuleType` 返回值 | 读源码字面量 vs 文档声明 | 极低 |
   | ERC-7579 module type id 合规性 | 断言返回值 ∈ {1,2,3,4} | 极低 |
   | `file:line` 锚点有效性 | 符号名检索存在性（**不用行号**，行号会漂移） | 低 |
   | 相对链接 404 | 解析 markdown 链接 → `Test-Path` | 低 |
   | pre-audit 声明存在性 | `grep` 关键文档必须含「not been externally audited」 | 极低 |

   **最后一条尤其重要**：本轮 COMPLIANCE 报告的「虚假 audited」已修复，
   但**这类失真是最容易复发的**（新增文档时容易漏写边界声明）。
   **声明一旦被机器守住，就不会再消失。**
