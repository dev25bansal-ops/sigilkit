## 1. 文档头部：统一 front-matter（**最高优先级**）

**现状**：65 份**全部**没有 front-matter。这是「无法生成站点、无法按状态筛选、无法排序」的直接原因。

**规范**：每份 `docs/*.md` 以如下块开头。**只加 3 个必填字段，不要更多** —— 字段一多，90% 的文档会填错或干脆不填：

```yaml
---
audience: [contributor]           # user | contributor | security-auditor | researcher
status: active                     # draft | active | superseded
updated: 2026-09-26                # last substantive update (not a reformat)
---
```

**为什么只这 3 个**：
- **`audience`** 是**唯一的选择器**。它同时解决两个问题：选哪套骨架（见 §2）与生成按读者分组的导航（见 `INDEX-2026-09-26.md`）。一个字段两个用途，**这是本规范里性价比最高的一项**。
- **`status`** 让「已作废」可机器识别，从而自动生成过期提示。
- **`updated`** 让陈旧度可度量。纯排版改动**不改**它（否则指标全被污染）。

**规则**：
- `audience` 用**固定枚举**（`user` / `contributor` / `security-auditor` / `researcher`），与 `INDEX-2026-09-26.md` 的分组一一对应。可多值（如 `docs/README.md` 是全部四类）。
- `status: superseded` 的文档在**正文顶部**加一行 `> **已作废**，请看 <新文档链接>` —— 不用额外的 `supersedes` 字段，人眼在文件开头就能看到。
- **本规范不要求 `layer` 字段** —— 层级已由 `STATUS.md` 的表格承载，front-matter 里再抄一遍就是**第二个事实源**，必然漂移。同理不加 `title`（H1 已经给了）、不加 `owner`（多数文档无单一维护者）。
- 若 `audience` 与 `STATUS.md` 的层级**冲突**，那是 bug：`STATUS.md` 是索引的索引，它赢。

**为什么不强制 `vault/`**：`vault/` 是 Obsidian vault，靠 `[[wikilink]]` + 末尾 `Tags:` 行组织，强加 front-matter 会与其工作流冲突。它在 `INDEX` 组 11 已单列，够用。

## 2. 正文结构：按 `audience` 选骨架，不要一套模板打天下

抽样发现：**用户文档**与**审计/计划文档**该用完全不同的骨架，混用才是当前「无模板」的根因。按 `audience` 选：

| `audience` | 必需骨架（章节按此顺序，缺失即 bug） |
|---|---|
| `user` | 前置条件 → 步骤（编号）→ 每步「期望输出 / 验证方法」→ 故障跳转。**禁止**出现未解释的内部代号 |
| `contributor` | 背景（为什么改）→ 现状 → 方案 → **影响面 / 破坏性** → **验证方式（可复制的命令）** → 回滚 |
| `security-auditor` | 结论摘要（表格先行）→ 威胁/发现（每条带 `file:line`）→ 严重度 → **缓解 / 未解决** → 引用前提（审计状态横幅） |
| `researcher` | 结论摘要 → 方法/口径 → 数据（每行给 primary source）→ **局限 / 未验证项** |

**贯穿要求（对所有 audience）**：
- **结论先行**：任何超过 1 页的文档，摘要表必须在正文第一屏。`PLAN-STATUS-2026-09-26.md` 的 §0 七行发现表、`GLOSSARY-2026-09-26.md` 的 §0 指标表是现有最佳实践。
- **摘要 / 正文**之间用 `---` 分隔，摘要不得依赖正文即可独立成篇。

## 3. 代码块与命令

**现状**：语言标注 87%；未标注的 12 个多为输出样例或 ASCII 架构图 —— 这两类**应该**标注：

````markdown
```text        # terminal output, error text, logs
```bash        # commands
```ts / ```solidity / ```json / ```yaml
````

**规范（命令）**：
- 每段命令**首行注明运行目录**，二选一：块前一行 `<!-- cwd: repo root -->`，或命令里显式 `cd`。`GETTING-STARTED.md` 的 `cd sigilkit` 是好范例，复制它。
- 破坏性 / 有副作用的命令（部署、广播、改链上状态、删文件）**必须在注释里标 ⚠️ 并写明前置条件**（owner key、testnet-first 等）。`DEPLOY-OPS-2026-09-26.md` 的 ⚠️/❌/✅ 分诊标注是现有最佳实践。
- 需人工确认的步骤给出**逐字可复制**的命令，不写「按需修改 X」这类模糊指令。

**规范（代码）**：跨语言一致性的示例（签名、Merkle 叶、ABI）应注明**与哪份 L1 代码对齐**，例如 `// byte-identical to MerkleWhitelist.sol v2 leaf format`。`PROJECT-MAP.md` 已建立这个文化，推广即可。

## 4. 链接与跨包引用

**现状**：两套体系 —— 用户文档用相对链接，研究文档用裸 http；`docs/` → `packages/` 的可点击链接**仅 1 条**。

**规范**：
- **`docs/` 内部**互相引用：用**相对路径**（`DEPLOYMENT.md`、`../SECURITY.md`）。[已达标]
- **`docs/` → 代码**：用**仓库相对路径 + 行号锚点**的可点击链接，而不是纯文本路径：
  ```markdown
  ✅ [`SessionKeyManager.sol:276-281`](../contracts/src/SessionKeyManager.sol#L276-L281)
  ❌ `SessionKeyManager.sol:276-281`   // 读者无法点击跳转
  ```
- **符号名 + 行号双锚点（最高价值的单条规则）**：在**会持续变动的仓库**里，只给行号必然漂移（本轮已实测 744→850→915 这类漂移，同一处代码在不同 agent 的报告里行号不同）。**行号供定位，符号名供漂移后重定位** —— 两者缺一，引用就会在几周内变成错误信息：
  ```markdown
  ✅ [`SessionKeyManager.executeWithSessionKey`](../contracts/src/SessionKeyManager.sol#L276-L281)（2026-09-26 快照，行号已漂移）
  ```
  凡引用测试、脚本、审计发现，一律带符号名。`PLAN-STATUS-2026-09-26.md` 已大量使用 `file:line`，补上符号名即可。
- **`docs/` → `packages/*/README.md`**：每份包 README 至少被一份文档以链接形式指向（当前 `indexer` 零入链 —— `INDEX-2026-09-26.md` 组 2 已补链）。
- **`docs/` → 外部**：必须给**可访问的 primary source**，付费/限流的要标注（`RESEARCH-NUMBERS.md` 已是范例）。[已达标]
- **不要用 `[[wikilink]]`**（`vault/` 内部除外）—— GitHub / VS Code 都不解析，跨目录还会断。

## 5. 命名规范

**现状量化**（`docs/` 43 份，按文件名）：

| 维度 | 现状 | 规范 |
|---|---|---|
| **大小写** | **UPPER 33 份（77%）** / Title-Case **5 份**（`Enhancements-2026-09-12`、`Issues-Catalog-2026-09-11/12/17/21-Agent-Review/23-C-Performance`）/ 混合 2 份（`PLAN-30-DAYS-…`、`WHITEPAPER-v2.1`） | 统一 **UPPER-KEBAB-CASE**（`STATUS.md` 的放置规则已要求 `<SUBJECT>-<YYYY-MM-DD>.md`，本规范补齐大小写） |
| **同 stem 冲突** | 靠日期区分 basename，本身有歧义（见下） | 新增前确认不撞名；日期是唯一区分位 |
| **日期格式** | ISO `YYYY-MM-DD` **35 份**；**8 份完全无日期**：`AC-01-SCRUB-PLAN`、`CI-WAIVERS`、`CONFIGURATION`、`DEPLOYMENT`、`GETTING-STARTED`、`RESEARCH-NUMBERS`、`STATUS`、`TROUBLESHOOTING` | **无日期 = 长期有效文档**（合理）；**有日期 = 快照/审计**，必须带 |
| **编号前缀** | `Issues-Catalog`（Title）与 `ISSUES-CATALOG`（UPPER）并存 | 一次性归一，不分批 |
| **中英混排** | 审计/研究文档标题多为中英混排（`SigilKit — Issues & Required Fixes 目录`） | 允许，但**目录名保持纯 ASCII**（`&`、`—`、空格在跨平台与 URL 编码上是持续摩擦点 —— `vault/` 22 份里已有 `Component 1 — …`、`Risk & De-risk Plan.md` 这类需 `%20%26%20` 转义的路径） |

> **一个真实的命名地雷**：`Issues-Catalog-2026-09-17.md`（Title）与 `ISSUES-CATALOG-2026-09-25.md`（UPPER）只差大小写与日期。macOS/Windows 默认文件系统**大小写不敏感**，任何按 stem 做的自动化（glob、索引检查）都会把它们视作同一族。`vault/` 的 4 份 `Component N — …` 用了 em-dash 前缀，也是同类问题。建议：新增文档一律 UPPER，存量在下次改名窗口统一。

## 6. 缩写与术语

**现状**：全量正则扫描 `docs/` 27 份，**无一例外地**在首次出现时**没有**全称展开：
- `MCP` —— **27/27 份**用到，无一处写「Model Context Protocol」
- `CI` —— **22/27 份**用到，无一处写「Continuous Integration」
- `SDK` —— **25/27 份**用到，无一处写「Software Development Kit」
- `E2E` —— **16/27 份**用到，无展开
- `UAT` —— 仅 `PROJECT-REVIEW-2026-09-17.md` 用到，也无展开

**规范**：
- **每份文档首次出现**该缩写时展开一次：`Model Context Protocol (MCP)`。仅首次，不是每段。
- `docs/GLOSSARY-2026-09-26.md`（118 条术语）是全库权威术语表 —— 写作时**先查它**，不要自造同义词。该表已指出 `rolling window` / `sliding window` 与代码的 `fixed (tumbling) window` 正面对撞，以及 `ERC-7702` 被误作规范名（7702 是 **EIP**）等 9 处术语误用。
- 命名一致性以 **L1 标识符**为准（`GLOSSARY` 的裁定规则）。文档与代码冲突时，改文档。

## 7. 数字

**规范**：
- 测试数 / 套件数 / CI job 数 / 覆盖率 / Halmos 规格数 —— 这些**由 `node scripts/check-doc-counts.mjs`（`npm run check:docs`）机器校验**，工具链赢过所有散文，包括 `STATUS.md` 与白皮书。[已达标]
- 外部事实（市场规模、采用率、漏洞编号、资助金额）—— 每行给 primary source，付费/限流的**显式标注**。[已达标，见 `RESEARCH-NUMBERS.md`]
- 写「已审计」「已验证」前先读 `STATUS.md` 的「audited」陷阱。本项目**尚无外部审计**；裸写 "audited" 是**事实错误**，不是风格问题。

## 8. 归档与生命周期

| 类型 | 放哪 | 命名 | 更新频率 |
|---|---|---|---|
| 用户参考 | `docs/`，L5 | `UPPER.md`（无日期） | 随行为变更 |
| 审计 / 评审 / 调研 / 策略 | `docs/`，L3 | `SUBJECT-YYYY-MM-DD.md` | 一次性快照，**过期即重跑而非修补** |
| 豁免登记 / 变更记录 | `docs/`，L2 | `UPPER.md` | 追加式，随发布 |
| 计划 | `docs/`，L3 | `PLAN-…-to-….md` | 高频，按设计过期 |
| 私密研究 | `vault/`，L4 | 现状命名 | 低；非规范 |
| **已作废** | `docs/` 原地保留 | 加 front-matter `status: superseded` + `supersedes` 链 | 冻结；不删除（删除会断已发布链接，参见 `vault/README.md` TD-8） |

**归档原则**：**已作废的文档保留、不删，只标状态。** `vault/README.md` 已给出理由（更正链指向它们，删目录会断已发布链接）；`STATUS.md` 已给出机制（`SUPERSEDED` 状态 + 索引行）。缺的只是 front-matter 里的机器可读标记 —— 这正是 §1 的价值。

## 9. 落地优先级（按投入产出排序）

1. **加 front-matter**（§1）—— 一次性成本最高、收益最大：直接解锁状态筛选、按 `audience` 生成子索引。**只加 3 个必填字段**：`audience` + `status` + `updated`。**不要加 `layer`** —— 层级已由 `STATUS.md` 承载，front-matter 里再抄一遍就是第二个事实源，必然漂移。
2. **归一文件名大小写**（§5）—— 修掉 `Issues-Catalog-2026-09-17`（Title）与 `ISSUES-CATALOG-2026-09-25`（UPPER）的文件系统歧义：**这不只是「不规范」，是会导致 glob / 索引检查误判同族的真风险**。改名须同一次改动内更新 `INDEX-2026-09-26.md`、`STATUS.md` 与所有引用方。
3. **把 `file:line` 升级为可点击链接 / 符号名锚点**（§4）—— 纯机械替换。**本轮价值最高的一项**：行号在持续变动的仓库里必然漂移（本轮已实测 744→850→915 这类漂移），**符号名 + 行号双锚点是唯一稳定的引用形态** —— 行号供定位，符号名供漂移后重定位。
4. **缩写首次展开**（§6）—— 轻量，可在 review checklist 里加一条。`MCP` 27/27、`CI` 22/27 份零展开，这个数字很刺眼。
5. ~~`packages/indexer/README.md` 补入链~~ —— **已完成**（`INDEX` 组 2）。

**不建议做的事**：不要为 `docs/` 引入统一的「背景/问题/方案/影响/验证」五段式模板 —— 审计类文档与用户文档的信息结构不同（见 §2），套同一模板会逼出无内容的小节。**按 `audience` 选骨架**是更省力也更诚实的做法。
