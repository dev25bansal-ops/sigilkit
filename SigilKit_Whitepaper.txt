2. Problem Statement & Market Context

 2.1 The Half-Decade-Old Open Issues

 The problem SigilKit solves is not theoretical. It is measurable, dated, and publicly visible on the issue trackers
 of the most-used libraries in the Ethereum ecosystem. OpenZeppelin issue #2793, opened in 2020 and still
 open today, requests an audited implementation of the EIP-2535 Diamond Standard -- the multi-facet proxy
 pattern that lets a smart contract exceed the 24KB contract size limit by routing calls across multiple
 implementation "facets". The issue has accumulated fifty upvotes, making it the single most-upvoted open
 issue across the OpenZeppelin, ethers.js, viem, wagmi, foundry, and hardhat repositories combined. In five
 years no audited implementation has shipped. Community alternatives exist but none has passed a formal
 audit, and the OpenZeppelin team has consistently declined to ship the pattern due to its complexity.

 ethers.js issue #1053, opened in 2019 and still open today, documents that the WebSocketProvider does not
 automatically reconnect when the underlying WebSocket closes -- a fundamental reliability gap that affects
 every frontend, every indexers, and every agent that listens for on-chain events. The issue has seventy-nine
 comments and thirty-three upvotes, and the underlying bug has survived three major ethers.js releases. The
 pattern recurs across the ecosystem: ethers.js issue #4469 documents "Could not detect network" errors in
 Next.js deployments (open 2.7 years, thirteen upvotes), and ethers.js issue #2030 documents fallback
 providers that hang indefinitely under failover (open 5 years, eight upvotes). Each of these is a face of the
 same underlying problem -- the EVM client libraries were never given a hardened, auto-reconnecting,
 multi-RPC transport layer.

 2.2 The EIP-7702 Tooling Gap

 EIP-7702 went live on Ethereum mainnet in May 2025 as part of the Pectra upgrade. It enables externally
 owned accounts (EOAs) to delegate execution to smart contracts without changing their address -- a
 foundational primitive for account abstraction, gas sponsorship, and session-key wallets. The standard is live,
 the wallets are broken, and the tooling does not exist. viem discussion #3285 ("EIP 7702 - Allow JSON-RPC
 Accounts to use") (twenty-five upvotes, open approximately one year). MetaMask issue #35520 documents
 that MetaMask silently rejects EIP-7702 authorization revocations (fourteen upvotes, twelve comments). And
 the Optimism Foundation itself posted an open Mission Request titled "EIP-7702 UX & Developer
 Tooling" -- an explicit, funded request for exactly the library that SigilKit Component 1 ships.

 The academic literature review confirms the gap. A search of arXiv, IEEE Xplore, and the ACM Digital
 Library for peer-reviewed papers on EIP-7702, session keys, or paymaster economics returns zero results. The
 2025 IC3 survey "Crypto x AI, AI x Crypto" explicitly finds that "most AI agent platforms show no evidence
 of real on-chain autonomy". Vendor blogs from Biconomy, ZeroDev, Turnkey, and Circle describe ad-hoc
 implementations, but no formal security model, no permission-graph analysis, no revocation-conformance
 framework exists. This is not just an engineering gap -- it is a publishable research gap, suitable for a
 peer-reviewed NDSS, USENIX Security, or CCS submission in 2027.

4. Solution Overview & Design Principles

 SigilKit is a four-component open-source toolkit. Each component is independently versioned and shippable,
 but together they form the missing standard-library layer for agent-native wallets. The design is opinionated by
 construction: every default is chosen to make the most dangerous agent behaviours impossible by default, and
 to make every primitive composable with the existing Ethereum and Base ecosystem. This chapter describes
 the component decomposition and the seven design principles that govern every architectural decision in the
 rest of this document.

 4.1 The Four Components

 Component 1 -- EIP-7702 Wallet Library. A hardened, wallet-agnostic library for EIP-7702 delegation.
 Exports authorize(), revoke(), validateAuthorization(), and a cross-wallet conformance test harness that runs
 against viem, ethers, MetaMask, and Coinbase Wallet on every commit. Built on Solidity 0.8.24 with UUPS
 proxy pattern and EIP-712 typed-data signatures.

 Component 2 -- Diamonds Module. An audited, OpenZeppelin-grade implementation of the EIP-2535
 Diamond Standard. Exports Diamond.sol, DiamondStorage.sol, FacetCutLib.sol, LoupeFacet.sol, and
 DiamondHarness.t.sol. Formally tested with Echidna and Slither-clean. Closes the most-upvoted open issue in
 the entire ecosystem.

 Component 3 -- Multi-RPC Provider. A hardened, auto-reconnecting multi-RPC provider with health
 checks, failover, and WebSocket reconnection. Exports createResilientHttp(), createResilientWs(),
 withFailover(), and healthCheck(). Drop-in replacement for viem and ethers transports -- closes the
 5.8-year-old ethers.js #1053 class of bugs.

 Component 4 -- Agent Session-Key Manager. An agent-first session-key manager with on-chain spend
 caps, per-window rate limits, target whitelists (via Merkle proofs), and a mandatory ActionLogged audit event
 per call. Exports SessionKeyManager.sol, SpendPolicy.sol, ActionLogger.sol, grantSessionKey(), and
 rotateSessionKey(). Fills an academic gap with zero peer-reviewed precedent.

4.2 Seven Design Principles

Standards-native, not standards-rewriting. SigilKit implements existing standards (EIP-7702, EIP-2535,
ERC-4337) rather than inventing new ones. The toolkit's value is in correctly implementing what the standards
already specify, with the production-grade hardening that the standards documents themselves do not provide.
New standards emerge from real usage; SigilKit's job is to make the existing ones safe to build on.

Composable, not competitive. SigilKit is designed to be imported by other wallet products -- Coinbase
Smart Wallet, Biconomy, Pimlico, ZeroDev -- rather than compete with them. The toolkit is the layer
underneath those products, not a replacement for them. This positioning is structural: each component
addresses a gap that the products themselves have requested be filled.

Agent-first defaults. Every default is chosen for the agent use case, not the human user case. The default
session key is scoped to a single target contract, expires in one hour, and has a spend cap equal to the smaller
of the wallet balance or a configurable per-action limit. A developer must explicitly broaden these defaults; the
safe path is the easy path.

Auditability by construction. Every successful call to executeWithSessionKey() emits an ActionLogged
event containing the agent identifier, target contract, value transferred, a hash of the agent's rationale, and a
block timestamp. This is not an optional log line; it is enforced in the contract. The result is that the entire
history of an agent's on-chain actions is reconstructable from on-chain data alone.

 Conformance-tested Against Real Wallets. Component 1's conformance harness is not a unit test against an
 idealised wallet -- it is a CI job that exercises viem, ethers, MetaMask, and Coinbase Wallet against the same

 MIT-licensed and openly developed. The entire toolkit is MIT-licensed and developed in the open from day

 Globally relevant. The toolkit cannot assume US-only context. RPC provider defaults include Alchemy,

5. System Architecture

 SigilKit is organised as four independently-versioned components, each addressing a single well-scoped gap.
 The components are layered: a wallet product imports Component 1 (EIP-7702 library) and Component 3
 (RPC provider) at the SDK level, deploys Component 2 (Diamonds module) and Component 4 (Session-Key
 Manager) at the contract level. This separation is structural, not cosmetic: it allows a wallet product to adopt
 individual components incrementally without an all-or-nothing migration, and it allows each component's audit
 and release cadence to be independent. This chapter walks through the layered architecture, the data flow for a
 representative agent transaction, and the dependencies between components.

 5.1 Layered Architecture

 The four components occupy two layers. Contract layer: Components 2 and 4 ship as Solidity 0.8.24
 contracts deployed on Base (with cross-chain deployment to Ethereum mainnet, Arbitrum, and Optimism as a
 configuration switch). Both use the UUPS proxy pattern for upgradeability under a 2-of-3 Gnosis Safe admin.
 SDK layer: Components 1 and 3 ship as a TypeScript package built on viem, with drop-in adapters for
 ethers.js. The SDK is stateless from the agent's perspective: it does not hold keys and it does not cache state,
 making it horizontally scalable across a fleet of agent processes.

 The two layers communicate through a thin boundary: the SDK encodes contract calls as EIP-712 typed data,
 signs them with session keys, and submits them via the resilient RPC provider. The contract layer validates the
 signatures, enforces the spend policy, executes the call, and emits the audit event. The strict separation means
 that a vulnerability in the SDK layer cannot bypass the contract layer's enforcement -- even a fully
 compromised SDK cannot authorise actions outside the session-key scope.

 5.2 End-to-End Data Flow

 A representative agent transaction -- say, an autonomous treasury manager swapping 50 USDC for WETH on
 Uniswap -- flows through the system in eight steps. The agent emits an intent; the adapter normalises it to a
 typed ActionRequest. Component 4 (SessionKeyManager) validates the request locally against the agent's
 SpendPolicy -- checking the spend cap, the call-target whitelist, and the per-window rate limit. If the policy is
 violated the request is rejected before any signature is created, costing zero gas and taking around five
 milliseconds.

 If the policy passes, Component 4 signs the request with the active session key using EIP-712 typed data.
 Component 3 (Multi-RPC Provider) picks the healthiest RPC from the pool, falls over on WebSocket drop,
 retries on transient failure. Component 1 (EIP-7702 Wallet Library) validates the authorization on chain --
 validateAuthorization() checks the delegation is active and non-revoked, with the conformance harness
 guaranteeing this matches every major wallet's behaviour. Component 4's SpendPolicy.enforce() runs onchain,
 checking the per-action cap, per-window cap, and Merkle-whitelist proof. If all pass, the inner call executes
 and the ActionLogged event is emitted. The SDK returns a receipt to the agent with the transaction hash, gas
 paid (sponsored via paymaster), action ID, and signed audit proof. End-to-end latency on Base is typically
 under 1.2 seconds.

 The four components are loosely coupled. Component 1 (EIP-7702 library) depends on Component 3 (RPC

6. Component Specifications

 This chapter specifies each of the four components at the API and contract level. For each component we
 document the public surface, the storage layout where applicable, the key functions, the events emitted, and
 the relationship to the underlying EIP. Code snippets are illustrative rather than complete -- the full
 implementation lives in the open-source repository and is subject to the audit described in Chapter 8.

 6.1 Component 1 -- EIP-7702 Wallet Library

 The EIP-7702 Wallet Library is a TypeScript package that provides hardened wrappers around EIP-7702
 authorisation flows. It exports four primary functions and a conformance test harness. The library is
 wallet-agnostic: the same authorize() call works against viem, ethers, MetaMask, and Coinbase Wallet, with
 the conformance harness verifying on every commit that all four wallets behave identically.

       // TypeScript API
       import { authorize, revoke, validateAuthorization } from '@sigilkit/eip-7702';
       import { createWalletClient } from 'viem';

       const wallet = createWalletClient({ /* viem config */ });

       // Authorise an EIP-7702 delegation to a wallet implementation contract
       const auth = await authorize(wallet, {
       implementationAddress: '0x...',
       chain: 8453, // Base
       });

       // Validate (on-chain + off-chain checks) that the delegation is active
       const isValid = await validateAuthorization(wallet, auth);
       //=> true | false | { error: 'REVOKED' | 'EXPIRED' | 'WRONG_CONTRACT' }

       // Revoke a delegation (cross-wallet safe -- closes MetaMask #35520)
       await revoke(wallet, auth);

 The conformance harness is the library's distinguishing feature. It is a Foundry test suite that exercises the
 same authorisation flow against four wallet implementations -- viem's test client, ethers' JsonRpcSigner, a
 MetaMask fork via Anvil, and a Coinbase Wallet fork -- and asserts byte-for-byte identical behaviour across
 all four. When MetaMask ships a breaking change to its revocation logic, SigilKit's CI fails before any
 downstream user is affected. This is the only credible way to ship a standard as new as EIP-7702, where the
 spec is live but wallet implementations are still stabilising.

 6.2 Component 2 -- EIP-2535 Diamonds Module

 The Diamonds Module is an audited, OpenZeppelin-grade implementation of the EIP-2535 Diamond
 Standard. It exports five files: Diamond.sol (the proxy), DiamondStorage.sol (the namespaced storage pattern),
 FacetCutLib.sol (the facet add/replace/remove operations), LoupeFacet.sol (the introspection facet), and
 DiamondHarness.t.sol (the Echidna + Foundry property-test harness). The module ships as a Foundry library
 that can be imported via forge install.

 correctness, storage isolation, and upgrade-path safety.

 6.3 Component 3 -- Multi-RPC Provider

 The Multi-RPC Provider is a TypeScript package that exports drop-in replacements for viem's http() and
 webSocket() transports and for ethers' JsonRpcProvider and WebSocketProvider. The provider maintains a
 pool of RPC endpoints, performs health checks every 30 seconds, and fails over automatically when an
 endpoint becomes unresponsive. The WebSocket implementation reconnects automatically on close, with
 exponential backoff and jitter, closing the ethers.js #1053 bug that has been open for 5.8 years.

       import { createPublicClient } from 'viem';

 The provider tracks per-endpoint latency, error rate, and rate-limit headers. Under failover it picks the
 healthiest endpoint from the pool, not just the next one in the list. The WebSocket implementation handles the
 four most common failure modes -- clean close, abnormal close, ping timeout, and TCP reset -- with the
 same reconnect logic, so the caller sees a single uniform "reconnecting" event rather than a chaotic mix of
 error codes. The provider is fully transparent: every failover is logged, every health check is observable, and
 the pool can be dynamically updated at runtime.

 6.4 Component 4 -- Agent Session-Key Manager

 The Session-Key Manager is the agent-first primitive at the heart of SigilKit. It exports three Solidity
 contracts -- SessionKeyManager.sol, SpendPolicy.sol, and ActionLogger.sol -- and a TypeScript SDK that
 wraps them. A session key is a secp256k1 public key granted a scope: a set of target contracts, function
 selectors, maximum gas per call, maximum spend per call, and an expiry timestamp. The scope is enforced in
 the contract, not the SDK, so a compromised SDK cannot bypass it.

Z.ai Engineering · July 2026  Page 17
SigilKit · Technical Whitepaper v2.0

       struct SessionKey {
       address[] allowedTargets; // Whitelist; empty = allow all
       bytes4[] allowedSelectors; // Whitelist; empty = allow all
       uint256 maxGasPerCall;
       uint256 maxSpendPerCall;
       uint64 expiry; // Unix timestamp; 0 = no expiry
       bool active;
       }

       function grantSessionKey(
       address key,
       SessionKey calldata scope
       ) external onlyOwner {
       require(scope.expiry > block.timestamp, "expiry in past");
       require(scope.maxGasPerCall > 0, "gas cap zero");
       sessionKeys[key] = scope;
       sessionKeys[key].active = true;
       emit SessionKeyGranted(key, scope.expiry);
       }

 The SpendPolicy contract enforces per-action and per-window spend caps. The per-action cap is checked on
 every call: if the call's msg.value plus any internal transfers exceeds the cap, the call reverts. The per-window
 cap is checked against a rolling window: the policy stores a spentThisWindow counter and a windowStart
 timestamp, with automatic window rollover. The ActionLogger contract emits an ActionLogged event
 unconditionally after every successful call -- there is no execution path that produces a state change without a
 corresponding audit event. This is the structural guarantee that makes agent actions reconstructable from
 on-chain data alone.

7. Security Architecture & Threat Model

Agent-controlled wallets are a high-blast-radius primitive: a single compromise can drain funds, manipulate
state, or cause an agent to take actions its operator never authorised. The security architecture of SigilKit is
designed around the assumption that every component will eventually be attacked, and that the contracts
themselves must be the last line of defence. This chapter walks through a STRIDE-based threat model, maps
each identified threat to a concrete mitigation in the protocol, and specifies the audit tooling stack used to
enforce the security posture continuously.

7.1 STRIDE Threat Model

The STRIDE framework -- Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service,
Elevation of Privilege -- provides a systematic way to enumerate the attack surface. For each category we
identify the specific vectors that apply to agent-controlled wallets and map them to a mitigation in the protocol
design. The model treats the agent itself as an untrusted component: even if the agent is compromised or
prompt-injected, the contracts should prevent catastrophic loss.

7.2 Agent-Specific Attack Vectors

Z.ai Engineering · July 2026                                                                               Page 19

 Beyond the standard STRIDE categories, agent-controlled wallets face three attack vectors that have no
 analogue in human-user wallets. Prompt injection is the most discussed: an attacker embeds instructions in
 data the agent reads (a webpage, a chat message, an API response) that cause the agent to issue a malicious
 transaction. SigilKit's defence is structural rather than algorithmic: even a fully-compromised agent cannot call
 a target outside its session-key scope, cannot spend past its per-window cap, and cannot execute after its
 session key expires. The blast radius of a prompt-injection attack is bounded by the session-key scope, not by
 the wallet balance.

 Key-exfiltration is the second vector: an attacker tricks the agent into leaking its session private key, e.g. by
 including a "debug" instruction that asks the agent to print its key. The mitigation is that session keys are
 short-lived (default one hour) and scoped (single target), so even a successful exfiltration has a small and
 time-bounded impact. Operators can also rotate session keys proactively via the SDK's rotateSessionKey()
 function. Composability attacks are the third vector: a malicious target contract attempts to re-enter the
 wallet during a callback, or to call back into the SpendPolicy to manipulate the window counter. The
 mitigation is a ReentrancyGuard on every state-changing function, plus the Checks-Effects-Interactions
 pattern enforced by code review and verified by Echidna property tests.

 7.3 Conformance Harness as Security Control

 Component 1's conformance harness is itself a security control. By running the same EIP-7702 authorisation
 flow against viem, ethers, MetaMask, and Coinbase Wallet on every commit, SigilKit detects wallet-side
 regressions before they reach production. When MetaMask silently rejected EIP-7702 revocations (issue
 #35520), the bug went undiscovered for weeks because no canonical library existed to test against. With
 SigilKit's conformance harness in CI, the same regression would be caught on the next commit -- not by a
 user losing funds. This shifts the burden of standards conformance from individual wallet teams to a shared,
 audited test suite, which is a structural improvement to the entire ecosystem's security posture.

8. Testing & Quality Assurance Strategy

 Production-grade smart contracts require a testing strategy that goes well beyond unit tests. SigilKit uses an
 eight-layer testing approach -- the standard seven layers plus a cross-wallet conformance harness unique to
 Component 1. This chapter describes each layer, the CI/CD pipeline that orchestrates them, and the rationale
 for the specific tool choices. The overall philosophy is: catch cheap bugs early (unit tests, linting), catch
 expensive bugs before mainnet (fuzz, invariant, audit), and catch unknown bugs in production (bug bounty,
 monitoring).

 8.1 The Eight Testing Layers

 Layer 1 -- Unit tests (Foundry). Per-contract tests that verify each public function behaves correctly on
 representative inputs. Coverage target is 95% line coverage across all four components. Each unit test is fast
 (under 100ms) and runs on every commit.

 Layer 2 -- Integration tests (Foundry). End-to-end tests that exercise the full user journey: deploy a wallet,
 grant a session key, sponsor a transaction, execute it, verify the audit event was emitted. Integration tests use a
 real ERC-4337 EntryPoint and a local bundler instance.

 Layer 3 -- Fuzz tests (Foundry --fuzz-runs 10000). Property-based tests where Foundry generates random
 inputs to a function and asserts an invariant holds. SpendPolicy and SessionKeyManager are the primary fuzz
 targets because their correctness depends on arbitrary combinations of inputs (any cap, any window, any target
 list).

 Layer 4 -- Invariant tests (Foundry --invariant). Higher-level property tests that assert global invariants
 hold across sequences of calls. Examples: "total spent across any window never exceeds the cap", "no session
 key can call an owner-only function", "the contract balance equals the sum of deposits minus the sum of
 withdrawals".

 Layer 5 -- Static analysis (Slither + solhint). Slither runs symbolic execution and dataflow analysis on the
 contract source to detect reentrancy, uninitialized storage, shadowing, and other patterns. Solhint enforces style
 rules that prevent common mistakes. Both run on every commit; new high or medium Slither findings block
 the merge.

 Layer 6 -- Property fuzzing (Echidna, nightly). Echidna is a more powerful property-based fuzzer than
 Foundry's built-in, with smarter input generation and longer run times. It runs nightly on the full contract suite,
 targeting the same invariants as Layer 4 but with a much larger search budget.

 Layer 7 -- Fork tests (Foundry --fork-url base). Tests that run against a live Base mainnet fork, using real
 Uniswap, Chainlink, and USDC contract addresses. Fork tests catch integration bugs with external protocols
 that local mocks cannot reproduce.

 Layer 8 -- Cross-wallet conformance harness (Component 1 only). A Foundry + Anvil test suite that
 exercises the same EIP-7702 authorisation flow against viem, ethers, MetaMask (via Anvil fork), and
 Coinbase Wallet (via Anvil fork). Asserts byte-for-byte identical behaviour across all four wallets. Catches
 wallet-side regressions before users do.

Z.ai Engineering · July 2026  Page 21
SigilKit · Technical Whitepaper v2.0

 Formal verification (Certora, pre-mainnet gate). Beyond the eight runtime testing layers, the most critical
 invariants -- specifically the four security invariants listed in Chapter 7 (INV-1 through INV-4) -- are
 formally verified using Certora Prover before each mainnet release. Certora takes specifications written in the
 Certora Verification Language (CVL) and proves, via symbolic execution and SMT solving, that the Solidity
 implementation satisfies the specification across all possible inputs and states. This is a stronger guarantee than
 fuzz testing: where Echidna and Foundry invariant tests check random sequences, Certora checks the entire
 state space. The pre-mainnet gate requires all four Certora specifications to pass with zero counterexamples;
 any counterexample blocks deployment until either the implementation or the specification is revised and
 re-verified.

9. Deployment & Operations

 Deployment strategy for SigilKit is deliberately conservative: testnet first, deterministic addresses, multisig
 admin, time-locked upgrades, and an external audit before any mainnet assets are placed under contract
 control. This chapter documents the deployment plan, the operational tooling, and the runbook for common
 operational tasks. The guiding principle is that every action on mainnet should be simulable, reversible within
 24 hours, and observable in real time.

 9.1 Multi-Chain Deployment

 SigilKit ships on four chains: Base (primary), Ethereum mainnet, Arbitrum, and Optimism. All four
 deployments use CREATE2 deterministic deployment, meaning the same deployer address with the same salt
 produces the same contract address on every chain. This has three operational benefits: developers can
 hardcode the SigilKit contract addresses in their SDK configuration regardless of which chain they target; the
 same SDK works on testnet and mainnet without code changes; and address-allowlisting on external contracts
 needs to be done only once and propagates across chains.

 The deployment sequence is staged across three environments. Base Sepolia and Ethereum Sepolia are the
 testnet targets -- every merge to main deploys to both testnets automatically via the CI/CD pipeline. Base
 Mainnet is the primary production target, deployed after the external audit is complete and the bug bounty has
 been live for at least two weeks. Arbitrum and Optimism mainnet are deployed in a second wave, one week
 after Base mainnet, to allow for staged rollout and monitoring.

 9.2 Upgradeability and Admin

 All contract-layer components (Components 2 and 4) use the UUPS proxy pattern. Upgrade authority is held
 by a 2-of-3 Gnosis Safe multisig with three signers: the project lead, an independent security engineer, and a
 time-locked backup signer that requires 24 hours to execute. Every upgrade transaction is wrapped in a
 TimelockController that enforces a 24-hour delay between proposal and execution, giving the community time
 to review and exit if they disagree with the upgrade.

 The SDK layer (Components 1 and 3) is versioned via npm and follows semantic versioning. Breaking changes
 require a major version bump and a migration guide. The conformance harness (Component 1) is run on every
 commit against the four supported wallets, so wallet-side breaking changes are detected immediately and a
 compatibility patch can be shipped before downstream users are affected.

 9.3 Operations and Observability

 Operational tooling is built around three pillars: Tenderly for transaction simulation and real-time alerting,
 Dune for public aggregate metrics, and The Graph for indexed event data. Tenderly simulates every upgrade
 transaction before it is signed by the multisig, so signers can see exactly what state changes the upgrade will
 cause. The Dune dashboard is public and surfaces metrics like total transaction volume through SigilKit
 wallets, active agent count, policies enforced, and failure rates.
